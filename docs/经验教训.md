# 经验教训

本文汇总 2026-10-10 从立项到手机端跑通这一轮里踩过的坑。每条都对应真实发生的事，写明现象、原因、以后怎么做。写在这里的目的只有一个：同类错误不再犯第二次。

---

## 一、mock 测试通过不等于验证通过

这是最贵的一条，本轮回合里因为它的返工占了大半。

现象一：测试里 `create_session` 的 mock 返回 `{"id": "ses_1"}`，真实接口返回 `{"data": {"id": "ses_1"}}`。测试全绿，手机一跑就 `KeyError: 'id'`。

现象二：流式文本聚合逻辑用 mock 事件测了三种语义全过，真实事件流里 `message.part.updated` 与 `message.part.delta` 出现次数为 0，手机端永远收不到文本。

现象三：`send_prompt` 的错误分支用 mock 测过，真实环境里模型调用 `question` 工具挂起等答案，bridge 不认识这个事件，手机端卡在「已收到」。

原因：mock 的字段形状是照自己的假设写的，等于自己出题自己答。凡是跨进程、跨服务的契约，mock 只能验证分支逻辑，不能验证字段。

以后怎么做：

1. 涉及外部系统的请求体、响应体、事件字段，一律先用真实调用或真实订阅取样本，样本落盘进项目，再照样本写代码与测试。
2. mock 只用于覆盖分支与边界，断言里不写死外部字段形状。
3. 交付前必须至少跑一次真实链路，跑不了就如实写「未验证」，不许用「应该可以」结案。

---

## 二、外部契约只能以真实样本为准

现象：从 opencode 二进制里用 `strings` 抠出 `message.part.updated` 的 schema，写进说明书并据此实现聚合。真实 SSE 事件流里根本没有这类事件，真实文本载体是 `session.text.started` / `session.text.delta` / `session.text.ended`，完成信号是 `session.execution.succeeded`。

原因：二进制里的字符串包含内部事件总线与 TUI 的名字，不等于对外的 HTTP/SSE 事件面。把线索当成了契约。

以后怎么做，核实手段按可信度排序：

1. 真实订阅样本，最高优先。
2. 本地 openapi.json 的契约（路径、请求体、响应体、枚举、错误码）。
3. 官方文档。
4. 二进制字符串、第三方客户端代码，只当线索，永远不当结论。

---

## 三、看结论要看完整字段

现象：查到一条 assistant 消息带 `completed` 时间戳，就断言「切换模型成功、2.8 秒正常完成」。补查 `content` 与 `finish` 才发现 `content=[]`、`finish=error`，它同样失败。完成时间戳只代表消息生命周期结束。

原因：只看了能支持结论的那一个字段，没有看决定成败的字段。

以后怎么做：判断一次执行成功与否，至少看四项：`content` 是否为空、`finish` 的值、`error` 是否为空、事件流里有没有成功信号。

---

## 四、排错顺序：先服务端真相，再代码

现象：「手机显示已收到，然后没动静」查了三轮。前两轮都在改 bridge 的流式与收尾逻辑。第三轮才去查服务端会话消息，一眼就看到 tool 部件 `name: question, state.status: running`，模型在等答案。

以后怎么做，遇到「没反应」类问题按这个顺序：

1. 查服务端会话的真实消息与状态，`GET /api/session/{id}/message`。
2. 查服务端有没有待答对象，`GET /api/session/{id}/form`、`GET /api/session/{id}/permission`。
3. 抓一段真实事件流样本，确认事件名与字段。
4. 最后才看 bridge 代码。

顺序反了会白改。

---

## 五、不许加用户没要求的东西

现象：模型提问导致死锁，我在 bridge 里实现了一整套表单交互：事件推送、编号选项、数字映射、重启兜底、七条测试。用户直接否掉，原话是「不要搞这种画蛇添足的事情」。用户的需求只有两条：手机端能直接和 opencode 对话做 vibe coding，模型用 CLI 同款。

原因：把「修好这个问题」理解成了「实现一个功能」。正确的解法是在项目目录关掉提问工具（一行配置），而不是写一套 UI。

以后怎么做：

1. 接到问题先复述用户原话里的需求，确认边界，再动手。
2. 能用一行配置解决的，不写代码。
3. 要加新能力前先问一句，不要先做完再等否。

---

## 六、叠加故障要分层定位，一次只改一层

现象：手机端不行，实际是两层独立故障叠在一起。第一层模型层，默认模型解析到 `github-copilot/claude-haiku-5.5`，该模型 baseURL 带 `/v1` 而网关实际路由不带，请求全返 404。第二层事件层，bridge 依赖的事件名在真实流里不存在。第一层修好后手机仍然没反应，看起来像「没修好」，实际是第二层还没修。

以后怎么做：

1. 每修一层就做一次可观察的验证（这次是真实 prompt 探测），确认这一层通了再进下一层。
2. 不要把多个改动塞进同一次交付，否则分不清是哪一层起作用。

---

## 七、脚本与进程纪律

1. 测试脚本与探测脚本必须落在项目 `tests/` 内，不许扔系统临时目录。本轮曾把探测产物丢在 `/private` 下，被用户当场指出。
2. 会发网络请求、可能计费的脚本必须带 `argparse` 与 `--dry-run`，并且打印请求数上界。本轮 `probe_opencode.py` 默认只打印计划，必须显式传 `--run` 才真跑。
3. 结束自己启动的进程按进程号精确关闭，禁止 `pkill` 模糊匹配。
4. 不要删正在被持有的锁文件。本轮为图清爽删了 `.bridge.lock`，而用户实跑的 bridge 正持有它的 flock，删掉等于让双实例保护对在跑的实例失效。锁的正确用法是只锁不删，测试用临时路径。

---

## 八、环境类坑，真机第一跑才会炸

1. 系统代理：本机装了 clash verge，终端里 `all_proxy` 是 SOCKS 代理。httpx 默认信任这些变量，访问 `127.0.0.1` 也往代理送，直接抛 `Using SOCKS proxy, but the 'socksio' package is not installed`。所有访问本机的 httpx 客户端都要 `trust_env=False`。
2. 系统代理不止影响 httpx。Clash Verge 还会把代理写进 macOS 系统代理设置，`scutil --proxy` 里 `SOCKSEnable` 为 1。`websockets` 的 `connect()` 默认 `proxy=True`，会读到这个 SOCKS 并因缺 `python-socks` 直接抛错，清空环境变量也一样中招。判定要看 `env -i` 下的 `urllib.request.getproxies()`；macOS 的 `proxy_bypass()` 只认系统例外列表，不读 `no_proxy`，环境变量侧堵不住。
3. 虚拟环境的 pip 坏了：`.venv/bin/pip` 的 shebang 指向旧目录名，直接调用报 bad interpreter。启动脚本装依赖统一用 `python -m pip`。
4. 启动脚本对端口与 URL 的解析要防空：`OPENCODE_BASE_URL` 不带端口时解析结果是空串，`opencode serve --port ""` 直接失败，必须回落默认端口。

## 九、退出路径必须真测

现象：Ctrl+C 刷一屏 traceback，`.serve_pid` 残留。原因是被取消的协程在 `finally` 里又 `await`，必然二次抛 `CancelledError`；脚本自己也收到同一份 SIGINT，清理代码走不走看运气。

改法与验证：bridge 用 `loop.add_signal_handler` 捕获信号置停止位再优雅退出；启动脚本用 trap 兜住自己的信号，确保清理代码确定性执行。验证方式是三层实测：单元层（停止位下 run 直接返回）、真信号层（给进程发 SIGINT 看退出码与日志）、脚本层（沙箱里真跑脚本加真 serve，发 SIGINT 看端口释放与残留文件）。

以后怎么做：任何退出路径都要有真信号测试，不能只看代码逻辑对。

2026-10-12 补充：真发信号也不够，还要在外部依赖一直失败的状态下发。当时企业微信长连接因系统 SOCKS 代理每 30 秒失败一次，`Bridge.run()` 卡在 `await self.link.start()`，永远走不到 `await self.stop_event.wait()`。信号处理器装上了，`_request_stop` 也 set 了停止位，但没人在等它，SIGTERM 与 SIGINT 全部无效，最后只能 SIGKILL。判据是日志里从头到尾没有「收到停止信号，正在退出」这一行。根因在 `aibot` 的 `connect()` 与 `_schedule_reconnect()` 互相递归，`max_reconnect_attempts=-1` 时永不返回。以后测退出路径，必须专门覆盖依赖不可用这条分支。

## 十、固化验证与回归注入

1. 每轮都要用的验证固化成一条命令：`./tests/run_tests.sh`，自带找空闲端口、按进程号清理、语法自检、接口契约核对。
2. 写完测试必须注入一个 bug 验证它能抓到回归。本轮注入过两次：把命令回复的收尾改成恒 `False`，报「命令回复仅最后一片收尾」失败；把建会话解包删掉，报「建会话解包 data」失败。
3. 测试断言用真实调用与比较，禁止用字符串匹配猜结果。
4. 测试运行不要污染真实日志，本轮加了 `tests/log_redirect.py` 把测试期日志重定向到临时目录。

---

## 十一、文档与结论纪律

1. 只写真实发生的事。没跑过的命令、没读过的文件，不许写成已完成。
2. 自己之前的结论错了，主动写明「上一轮我说 X，这是错的」并记下错因，不许悄悄改掉。
3. 未核实的一律标「未验证」。本轮遗留项：企业微信 markdown 字符上限、权限卡片点击事件的真实字段形状。

## 十二、菜单编号 1、2 是系统快捷键，永远不进模型

现象。2026-10-27 凌晨，用户在手机上点企业微信机器人自带的按钮菜单，平台送来纯文本 1 和 2。桥接把它们当成普通指令转给模型，模型读成「两条 MCP 路线二选一」，接着执行了 Blender 安装，占了 2.1G 磁盘，还卡死十几分钟。

原因有两层。

1. 代码按 180 秒时间窗判断菜单，窗口没打开就把数字降级成指令。时间窗是当时照 README 实现的，而 README 本身就是错的。
2. 第五节已经记过用户原话「不要搞这种画蛇添足的事情」，动手前没有先读这一节，同一个原则又踩了一遍。

现在怎么做。

1. `_on_text` 在任何会话锁之外先判菜单，编号命中就直接执行，不排队、不进模型。
2. 没有时间窗。`menu_shown` 只用于心跳记录，不再参与拦截。
3. README 的命令表同步改成「任何时刻发 1 都直接执行」，避免下一轮又照错文档实现。
4. 改这个项目之前，先读本节和第五节。
