# 锁屏、休眠与消息可靠性：为什么锁屏后机器人不回复

本文回答一个问题：Mac mini 锁屏之后，企业微信机器人为什么不再回复消息，以及为什么必须阻止系统休眠。所有结论分两类来源，本机实测与外部资料，逐条标注。凡是没有证据的地方明确写成待核实，不做推测性断言。

调查时间 2026-10-11，对象是本项目 wecom bridge 与电脑上同时运行的 Hermes agent。

## 1. 结论摘要

1. 锁屏本身不会让进程停下。真正掐断消息的是锁屏之后系统进入的休眠状态。系统休眠时全部用户进程被冻结、网络断开，机器人收不到任何消息。
2. 本项目用的是企业微信长连接模式，连接由本机主动向企业微信发起。休眠期间这条连接断开，企业微信不会把休眠期间的消息补投回来，所以那几条消息永远不会得到回复。
3. 唤醒之后还有一段二次丢消息窗口。SDK 每 30 秒发一次心跳，连续 2 次收不到回应才判定连接已死并重连，实测唤醒后要 20 到 46 秒才恢复订阅，这段窗口内到达的消息同样丢。
4. Hermes 并不是免疫。本机日志显示它在同一个休眠窗口同样断连、同样发消息失败。它给人没事的印象，是因为它有定时任务的补跑机制，错过了的定时任务会在唤醒后补一次，所以表现为晚到但会到，而不是实时收到。
5. 因此，要让机器人锁屏期间也能实时回复，唯一可行的做法是阻止系统休眠。可选项有三个，本项目的选择是启动脚本里用 caffeinate 包住 bridge 进程。

## 2. macOS 的锁屏与休眠不是一回事

很多人把锁屏、屏幕熄灭、系统休眠当成一件事，它们在 macOS 里是三件不同的事，后果完全不同。

| 状态 | 英文与钩子名 | 进程是否运行 | 网络是否可用 |
| --- | --- | --- | --- |
| 锁屏 | lock screen | 运行 | 可用 |
| 显示器休眠 | display sleep | 运行 | 可用 |
| 空闲系统休眠 | idle system sleep | 冻结 | 断开 |
| 维护休眠 | maintenance sleep 与 DarkWake 循环 | 周期冻结与短暂解冻 | 断续 |

本机 2026-10-11 的实测取值来自 `pmset -g`：

1. `sleep 1`，系统空闲休眠定时。
2. `displaysleep 180`，显示器 180 分钟后熄灭。
3. `powernap 1`，开启 Power Nap。
4. `womp 1`，开启 Wake for network access。
5. `tcpkeepalive 1`，休眠期间保持 TCP 连接。

`pmset -g log` 在这一天里统计到 536 条进入休眠记录。也就是说锁屏之后机器不是偶尔睡，而是持续在睡与短暂醒之间循环。

### 2.1 Power Nap 不等于后台跑程序

Apple 官方对 Power Nap 的说明是，休眠期间它只做这些事：检查邮件、更新日历与 iCloud 事件，接电源时还可以下载软件更新、做 Time Machine 备份。

来源：Apple 支持文档关闭或开启 Power Nap，mh40774。

这条很关键。Power Nap 不会替任意后台程序收发消息，它只是一组系统内置服务的维护窗口。指望 Power Nap 让机器人在休眠期间收消息，方向就是错的。

### 2.2 唤醒不能被网络请求触发

休眠中的机器不会因为一条普通的入站网络请求而醒来。Apple 开发者论坛的讨论指出，通过 Wake on LAN 之类的网络事件唤醒，机器只会进入 darkwake，一种部分唤醒状态，不会完全唤醒系统。Apple 支持文档也说明，唤醒休眠机器要用的是 Bonjour 睡眠代理那一套，只对特定服务有效。

来源：Apple 开发者论坛线程 771999，Apple 支持文档 mchlp2995。

对企业微信长连接来说更直接：连接是本机主动向 `wss://openws.work.weixin.qq.com` 发起的。企业微信手里没有一个能反向把本机叫醒的通道。机器睡着了，它就没有办法把消息送达，这是架构决定的。

## 3. 企业微信长连接在离线期间不补投

来源：企业微信开发者中心，智能机器人长连接，路径 101463，最后更新 2026/05/25。

### 3.1 官方自己承认长连接更脆

文档里的长连接与短连接对比表原文：

| 特性 | Webhook 短连接 | WebSocket 长连接 |
| --- | --- | --- |
| 服务端要求 | 需要公网可访问的 URL | 无需固定的公网 IP |
| 复杂度 | 低 | 较高，需维护心跳 |
| 可靠性 | 高，无状态 | 需要心跳保活、断线重连 |

选择长连接的代价就写在可靠性这一行里。它换来的是免公网 IP、免加解密、低延迟，付出去的是可靠性要自己扛。

### 3.2 心跳与超时断开

官方原文：

1. 连接建立成功后，开发者需定期发送心跳请求保持连接活跃，防止连接被服务端主动断开。
2. 超时断开：若长时间未收到心跳，服务端会主动断开连接。
3. 断线重连：开发者需实现断线检测和自动重连机制。

同一份文档里唯一提到断线重传的地方，是上传临时素材的分片：如果连接断开后重连，只要上传会话未过期，可以继续上传未完成的分片。

### 3.3 消息回调不补投

整份文档没有任何一处说，开发者离线期间的消息会在重连后补发。对照 3.2 节的断线重传只出现在文件分片上传，可以判断普通消息回调不做补投。

这一点另有一条本地旁证。本机 bridge 日志里，每次休眠唤醒后重连成功都只收到当下的新消息，从没有出现重连后补来一批休眠期间消息的情况。所以本节结论标注为已核实到官方文档层面，但官方没有一句正面否决，属于从文档结构与本地观察共同得出的判断。

### 3.4 单连接限制

同一机器人同一时间只能保持一个有效长连接，新连接会踢掉旧连接，旧连接收到连接断开事件。这条与本问题相关的点在于，休眠唤醒后的重连会把连接抢回来，属于正常行为，会导致旧连接报一次断开，不是故障信号。

## 4. SDK 的断线检测有延迟

本项目用的 Python SDK 是 `wecom-aibot-python-sdk` 1.0.2，源码已在本机 venv 里读。

关键取值：

1. `heartbeat_interval` 默认 30000 毫秒，即每 30 秒一次心跳。
2. `_max_missed_pong` 等于 2。
3. 心跳循环每 30 秒发一次 ping，每次发送前先看连续未收到 pong 的次数，达到 2 次就判定连接已死，关闭底层连接并触发重连。

machine 休眠时这条心跳循环也跟着冻结。唤醒之后它恢复运行，但底层套接字其实早已断开。要等到 2 个心跳周期走完，也就是最多约 60 秒，SDK 才会发现并关闭重连。

这解释了实测里唤醒后 20 到 46 秒的恢复延迟。这段窗口叫二次丢消息窗口，机器已经是醒的，但订阅还没恢复，消息照样丢。

## 6. Hermes 为什么看起来没事

这是这次调查里最值得说清的一点。结论是，Hermes 不是不受影响，它的应对方式与本项目不同。

### 6.1 Hermes 用的是同一条企微长连接

Hermes 的 `channel_directory.json` 里有 wecom 渠道，用户是 FanChuang。它的日志里反复出现企微适配器的 ping 记录，形态与企业微信官方长连接一致。

休眠窗口内 Hermes 的日志同样完全停摆。它自己的日志原文：

1. `[Wecom] WebSocket error: WeCom websocket closed`
2. `[Wecom] Send failed: WeCom connection interrupted`
3. `[Wecom] Failed to send media ... WeCom websocket is not connected`
4. `[Wecom] Reconnected`

也就是说，Hermes 在休眠期间同样断连，同样在唤醒后有一段时间发不出去消息。所谓 Hermes 锁屏后还能发消息，不是因为它实时在线。

### 6.2 真正的差异是定时任务补跑

Hermes 的 cron 调度器有一整套错过补跑逻辑，源码在 `cron/jobs.py`：

1. `_classify_dispatch_lateness` 把迟到分三档，`on_time`、`late`、`catch_up`。
2. `catch_up` 的语义原文是，超出宽限窗口的、累计的错过被跳过，但在当下补执行一次。
3. 每次补跑会调用 `record_catch_up_occurrence`，把 cron 目录下的 `catch_up_occurrences` 计数加一。

本机证据：`catch_up_occurrences` 的内容是 431，修改时间是 20:13:34，正好在 20:13:18 唤醒之后 16 秒。

所以 Hermes 给人的体验是，定时提醒、异步任务结果这类消息，锁屏期间攒着，唤醒后补一次发出来。晚到，但会到。这跟实时收消息是两回事。

### 6.3 Hermes 自己的文档也要你阻止休眠

Hermes 自带文档有一节专门讲 macOS 的 caffeinate，原文给的用法包括：

1. `caffeinate -dis`，阻止显示器、空闲与系统休眠。
2. `caffeinate -i -w $(cat ~/.hermes/gateway.pid)`，只要网关进程活着就一直顶着。

来源：本机 `~/.hermes/hermes-agent/website/docs/user-guide/multi-profile-gateways.md` 第 1019 节起。

也就是说，Hermes 的作者同样认为必须阻止系统休眠，这与本项目的判断一致。

### 6.4 Hermes 自己也踩过休眠的坑

Hermes 的公开仓库有一条已确认的 issue，编号 44183，标题是睡醒之后桌面会话丢失。里面有一个很有价值的判断：`time.monotonic()` 在休眠期间不前进，因为它对应 `mach_absolute_time`，而 `threading.Timer` 走的是实时时钟，休眠期间照样走。这类时钟域问题正是休眠带来的隐蔽故障。

来源：GitHub NousResearch/hermes-agent issue 44183。

### 6.5 一句话概括差异

同一台机器，同一类长连接，休眠期间两个程序都收不到消息。差别在唤醒之后：Hermes 有持久化任务队列与定时补跑，把欠下的主动消息补发出来；本项目只负责把收到的消息转成 prompt，没有离线队列，没收到就是没收到。用户感受到的 Hermes 还能发消息，本质是补跑，不是在线。

## 7. 为什么必须禁止系统休眠

把上面几条串起来，第一问的答案就有了。

1. 企业微信不会在离线期间缓存并补投消息回调，只有文件分片上传支持断线续传。
2. 连接由本机主动发起，企业微信没有通道把休眠的机器叫醒。
3. 系统休眠期间进程无 CPU、无网络，任何写在本机的方案都不可能收到消息。
4. 即使勉强靠网络事件唤醒，macOS 也只是 darkwake，部分唤醒，不能保证用户进程恢复正常。

所以只要目标是锁屏期间实时回复，就必须让机器别睡。没有第四条路。

如果接受晚到，可以不休眠管理，靠一条离线队列加唤醒后补发来兜底。这需要自建队列，企业微信不提供。这是另一种技术路线，不是本问题的默认答案。

## 8. 本项目的方案与取舍

`just_run.sh` 拉起 bridge 的那一行改成：

```
caffeinate -ims "$PY" bridge.py
```

取舍说明：

1. 选 `-i` 阻止空闲系统休眠，这是锁屏后触发休眠的直接原因。
2. 选 `-m` 阻止磁盘空闲休眠，避免长任务期间磁盘睡眠引发的问题。
3. 选 `-s` 在交流电下阻止系统休眠。Mac mini 一直插电，这一条属于加固。
4. 不加 `-d`。这样显示器照常熄灭、屏幕照常锁，只有机器本体不睡。
5. 断言由 bridge 进程自己持有，bridge 一退出就自动释放，不动用户其它电源设置，可逆。

caffeinate 各选项语义来自 macOS 手册 caffeinate 第 8 节：`-i` 阻止空闲休眠，`-m` 阻止磁盘空闲休眠，`-s` 在交流电下阻止系统休眠，`-d` 阻止显示器休眠，带 utility 参数时断言随该进程结束而释放。

## 9. 备选方案

1. 系统级永久不休眠：`sudo pmset -a sleep 0`，需要管理员密码，影响全局，本项目未采用。
2. 关闭 Power Nap：`sudo pmset -a powernap 0`，需要管理员密码。它只减少维护唤醒，不能替代阻止休眠。
3. 交给 launchd 常驻：把 bridge 也做成 LaunchAgent，配 KeepAlive，崩溃与重启后自动拉起。它解决进程不在的问题，不解决休眠期间收不到消息的问题。可与 caffeinate 叠加。

## 10. 未核实与待验证

1. 企业微信官方没有一句话正面写明离线期间消息回调不补投，本文结论来自文档结构推断加本地观察，标注为高置信推断，不是官方原文。
2. 唤醒到重连的延迟上限，本文按 SDK 的 2 次丢失 pong 与 30 秒心跳推算出约 60 秒，实测样本是 20 到 46 秒，样本量只有两次。
3. 重启 bridge 并锁屏后的端到端验证尚未做，需要真实锁屏场景复测。
4. Hermes 是否存在针对入站消息的离线补投，未找到证据，仅确认其定时任务有补跑。若确实观察到锁屏期间发给 Hermes 的实时消息也在唤醒后被回复，需要单独采样它的入站路径，不能沿用本文结论。
